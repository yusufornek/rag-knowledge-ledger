# ADR 0003: v0.1.0 release scope

## Status

Accepted

## Context

The project specification (section 27) defines ten milestones, M0
through M9, culminating in a v1.0 release that includes a FastAPI
server, PostgreSQL/Redis/S3-backed persistence, background workers,
authentication and workspaces, and a Next.js web UI (M7 and M8), on top
of the deterministic core, pipeline, CLI, connectors, and reconciliation
engine (M0 through M6). Building all of M0-M9 before any usable release
exists would mean a very long period with nothing an external user or
contributor could install and run, and would put a large amount of
security-sensitive surface (credential storage, SSRF-exposed target
configuration, multi-tenant auth, a browser-facing UI) into a first
release before the deterministic core it depends on has been exercised
and hardened on its own.

## Decision

v0.1.0 targets a standalone, CLI-first product: the deterministic
manifest core (canonicalization, identity, signing), the source
discovery/parse/chunk/embedding pipeline, the CLI, the Qdrant and
pgvector connectors together with the NDJSON portable connector, and the
reconciliation and policy engine. In milestone terms, this is M0 through
M6. The server API, persistence layer, job orchestration, and web UI
(M7 and M8) are explicitly deferred to a later release and are not part
of v0.1.0.

This is a scope decision, not a change to the specification's eventual
v1.0 target: the specification remains the authoritative description of
the full product, and M7/M8 work is expected to follow v0.1.0 using the
same domain model, manifest format, and reconciliation engine built in
M0-M6, without redesigning them.

## Consequences

- v0.1.0 is usable entirely as a local CLI tool plus a Python SDK,
  against manifests on disk and read-only connections to a Qdrant
  instance or a PostgreSQL/pgvector database that the user already
  operates. It has no server component, no stored credentials, no
  multi-user auth, and no browser UI.
- Everything the specification describes as workspace-, token-, or
  credential-storage-related (for example `FR-001` through `FR-005`)
  is out of scope for v0.1.0, since those requirements exist to support
  the server/API layer built in M7. `IMPLEMENTATION_STATUS.md` tracks
  these as `pending` against the full specification while noting they
  are not v0.1.0 commitments.
- Target credentials for the CLI in v0.1.0 are supplied through
  environment variables or local configuration read directly by the
  connector at run time, not through an encrypted credential store;
  AES-256-GCM at-rest credential encryption (`FR-003`) becomes relevant
  once the server persists credentials in M7.
- This choice means the project can reach a genuinely complete,
  tested, documented v0.1.0 release (README claims match what is
  installable) rather than shipping a partially implemented server and
  UI alongside a complete core. It also means early adopters and
  connector contributors interact with the tool as a CLI first, which
  matches how the specification's own personas (AI/LLM Engineer,
  Platform Engineer) are described as using it in CI gates and local
  investigation (UC-01 through UC-04, UC-06).
- The web UI's lineage explorer (UC-06, `FR-141`/`FR-142`) is not
  available in v0.1.0; the same lineage drill-down is expected to be
  reachable through CLI/report output (JSON/HTML) instead.
